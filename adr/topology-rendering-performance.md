# 구조 뷰 렌더링 기술·성능 기준

## Concern
토폴로지 다이어그램(구조 뷰)을 어떤 기술로 렌더링하고, 대용량 이벤트(≤100만) 리플레이 시 어떤 성능 기준을 적용할 것인가?

## Status
approved

## Context
- 구조 뷰 = 기본 화면. 링크 위 프레임 애니메이션, 노드 상태(태스크·오버런·큐) 하이라이트, 게이트웨이 라우팅·스위치 드롭 표시, 클릭 인터랙션 (PRD v2).
- 기술 스택 = React/TypeScript + Vite (ASR-014). 데이터 흐름 = 코어 임베드 + 일괄 JSON (ASR-015) — 프런트엔드가 전체 이벤트 보유, 로컬 재생·시크.
- v1 아키텍처 정의 규모: ECU·스위치·게이트웨이·앱·태스크 — 실용적 토폴로지는 수십 개 노드·수백 개 링크 수준 (그래프의 절대 규모가 크지 않음). 대용량은 **이벤트 수(≤100만)** 쪽.

## Decision
**Option A — SVG + React 커스텀 컴포넌트 (D3 레이아웃 보조)**
사용자 위임 계속 진행 (2026-08-12 auto-continue): React가 SVG 노드/링크 렌더, D3는 레이아웃 계산만. 성능 기준 — 노드 ≤200/링크 ≤500에서 60fps, ≤100만 이벤트 로드·정렬 ≤ 2s, 시크 반영 ≤ 100ms.

## Options
### Option A — SVG + React 커스텀 컴포넌트 (D3 레이아웃 보조) (권장)
- React가 SVG 노드/링크를 렌더, D3는 레이아웃 계산(자동 배치)에만 사용. 링크 프레임 애니메이션은 SVG stroke-dashoffset/CSS 트랜지션, 상태 하이라이트는 CSS 클래스 토글.
- Pro: DOM 기반이라 React 상태·이벤트(클릭/툴팁)와 자연 통합, 개발 속도·디버깅 최고, 토폴로지 규모(수백 요소)에서 성능 충분, 리플레이 상태 갱신은 변화 요소만 업데이트
- Con: 요소 수가 수천을 넘으면 DOM 오버헤드 (현 요구에선 해당 없음)

### Option B — Canvas 2D 커스텀 렌더
- 단일 캔버스에 직접 그리기 — 대량 요소 애니메이션 성능 최고.
- Pro: 요소 수 무관한 그리기 성능
- Con: 히트 테스트·툴팁·인터랙션 직접 구현, React 상태와 수동 동기화, 개발 비용 큼 — 수백 요소 토폴로지엔 과잉

### Option C — 그래프 라이브러리 (Cytoscape.js / vis-network 등)
- 노드/엣지 관리·레이아웃 내장.
- Pro: 그래프 기능 기본 제공
- Con: **커스텀 오버레이(링크 프레임 애니메이션·게이트웨이 라우팅·스위치 드롭 표시)가 라이브러리 데이터 모델에 제약** — v2 핵심 UX를 라이브러리에 맞게 각색해야 함. React 통합도 이중 관리

## Tradeoffs
| 차원 | A (SVG+React) | B (Canvas) | C (그래프 라이브러리) |
|---|------|------|------|
| 커스텀 오버레이 자유도 | ★★★ | ★★★ | ★ (모델 제약) |
| React 통합 | ★★★ | ★★ | ★★ |
| 개발 속도 | ★★★ | ★ | ★★ |
| 토폴로지 규모 (수백) 성능 | ★★★ | ★★★ | ★★★ |
| 인터랙션(툴팁/클릭) | ★★★ | ★★ | ★★ |

## Recommendation
- **Option A (SVG + React, D3 레이아웃 보조)** 권장. v2 핵심(링크 프레임 애니메이션·노드 상태 하이라이트·게이트웨이 라우팅 표시)을 자유롭게 커스텀할 수 있고, 토폴로지 규모가 작아 SVG 성능으로 충분. 리플레이 성능은 이벤트 인덱싱·상태 스냅샷으로 확보.

## Consequences
- **성능 기준 (Spec에 인코딩할 기준):**
  - 토폴로지 렌더·인터랙션: 노드 ≤200 / 링크 ≤500에서 60fps 목표
  - 이벤트 로드·정렬 (서버): ≤100만 이벤트 파싱·정렬 ≤ 2s
  - 시크(탐색): 임의 시각 점프 후 노드·링크 상태 반영 ≤ 100ms
- 렌더링은 SVG — Canvas 전환은 비목표 (규모 한계를 넘는 경우에만 재검토).
