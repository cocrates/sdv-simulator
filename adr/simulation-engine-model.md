# 시뮬레이션 엔진 모델 (Simulation Engine Model)

## Concern
시뮬레이션을 어떤 시간 진행 모델로 구동할 것인가? (이산 사건 / 주기 기반 / 연속 시간)

## Status
approved

## Context
- ASR-001 승인됨: Python
- 검증 도구로서 **결정성(determinism)** 필수 — 같은 입력 → 같은 출력 (회귀 테스트의 전제)
- v1 범위: E/E 아키텍처 + 차량 내 통신(CAN/Ethernet 지연·대역폭·라우팅) + 앱 런타임(가상 노드 SW 실행)

## Decision
**Option A — 이산 사건 시뮬레이션(DES) 기반 + 주기 태스크 하이브리드**
User-approved: 코어는 이산 사건 엔진(이벤트 큐). 앱 런타임의 주기 태스크는 스케줄러가 이벤트로 생성·실행. 단일 스레드 + 고정 이벤트 순서로 결정성 보장.

## Options
### Option A — 이산 사건 시뮬레이션 (Discrete-Event Simulation, DES)
- 이벤트 큐 기반. 각 이벤트가 특정 시각에 발생하며, 메시지 전송·도착·태스크 실행을 이벤트로 모델링 (ns-3, OMNeT++ 방식)
- Pro: 지연·대역폭·큐잉·게이트웨이 라우팅을 정확히 재현. 이벤트가 없으면 시간을 도약(fast-forward)하므로 대규모 시나리오에 효율적. 결정적
- Con: 자동차 SW의 주기적 태스크(CAN 주기 메시지, RTE 태스크)를 이벤트로 변환하는 추상화가 필요

### Option B — 주기 기반/시간 슬라이스 (Time-step)
- 고정 시간 간격마다 모든 컴포넌트를 순차 실행 (AUTOSAR RTE/cyclic task 모델에 가까움)
- Pro: 자동차 SW의 주기 태스크 모델과 자연스럽게 일치, 구현 단순
- Con: 지연·대역폭·경합을 정확히 모델링하기 어려움. 시간 간격이 작을수록 느려지고, 이벤트 정확성이 떨어짐

### Option C — 연속 시간 (물리 기반)
- 미분 방정식 기반 시간 진행 (차량 동역학 등 물리 시뮬레이션에 적합)
- Pro: 물리적 정확성
- Con: 차량 SW 플랫폼(메시지·소프트웨어 동작) 검증에는 과도. 결정성·구현 복잡도 불리

## Tradeoffs
| | DES (A) | Time-step (B) | Continuous (C) |
|---|---------|---------------|----------------|
| 통신 지연·대역폭·라우팅 재현 | ★★★★★ | ★★★ | ★★ |
| 앱 주기 태스크 모델 적합성 | ★★★★ (하이브리드 시) | ★★★★★ | ★★ |
| 결정성 | ★★★★★ | ★★★★★ | ★★★ |
| 구현 단순성 | ★★★ | ★★★★★ | ★★ |
| 대규모 시나리오 효율 | ★★★★★ | ★★★ | ★★ |

## Recommendation (optional)
- **Option A (DES) 기반 + 주기 태스크 하이브리드** 추천: 코어는 이산 사건 엔진으로 두고, 앱 런타임의 주기 태스크는 스케줄러가 이벤트로 생성·실행.
  - v1의 핵심 검증 대상(통신 지연·라우팅·대역폭)을 정확히 재현
  - 자동차 SW의 주기적 특성(RTE 태스크)도 이벤트로 표현 가능
  - 단일 스레드 + 고정 이벤트 순서로 결정성 보장

## Consequences
- 앱 런타임(ASR-005)은 주기 태스크를 스케줄러 + 이벤트로 구현해야 함
- 시뮬레이션 시간 해상도(ms/us)와 통신 충실도(ASR-004)가 연결된 설계 필요
- 시간 도약 구현으로 긴 시나리오도 빠르게 실행 가능
