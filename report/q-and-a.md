# Q&A — 독자 관점 예상 질문과 답변

> 구조 설계서(`architecture.md`)를 처음 읽는 독자(과제 평가자)가 가질 법한 질문을 정리한 문서.
> 본문에서 충분히 답이 되는 항목은 참조만 표기하고, 보강이 필요하거나 추가 설명이 유용한 항목은 보충 제안을 기록한다.
> 날짜: 2026-08-13

## Q1: 시뮬레이션이 "결정적"이라고 하는데, 같은 입력이 항상 같은 결과를 주는가?

**A:** 그렇다. 4.1절의 시간 모델에서 모든 이벤트는 `(t_ms, priority, decl, seq)` 완전 순서 키로 정렬된다.
같은 tick에서도 우선순위·선언 순서·시퀀스 번호로 순서가 고정되므로, 같은 입력이면 항상 같은 이벤트 로그가 산출된다.
결정성은 2.4절의 핵심 설계 특성 ①이며, 13장 결론에서 본문 전체를 통해 확인된다고 재검증한다.
**Supplementation:** 없음 (4.1·4.3절이 단계적으로 설명).

## Q2: 통신 충실도(CAN/Ethernet) 모델이 실제 하드웨어와 어느 수준까지 일치하나?

**A:** 4.4절 참조 — L2(링크 계층) 수준 충실도. CAN은 프레임 전송 시간 수식(bitrate 기반)과 ID 중재,
버스 큐잉을 시뮬레이션하고, Ethernet은 스위치 FIFO 큐·테일 드롭·supersede(동일 프레임 교체)를 시뮬레이션한다.
충실도 수준 선택 자체가 설계 결정이며, 근거는 부록 C.3.1(통신 충실도 L2)과 부록 D의 해당 ASR 항목에 있다.
**Supplementation:** 없음.

## Q3: v1과 v2는 별개의 구현인가? 대시보드가 코어를 다시 만들었나?

**A:** 아니다. v2(웹 대시보드)는 v1 코어(`sdv_sim/core`)를 **변경 없이** 재사용한다.
9.2절 — v2가 요구한 유일한 코어 확장은 F-11 방향 전환의 `loads()` 문자열 입력 API 추가였고,
이는 기존 `load()`(파일 경로)에 더해진 하위 호환 API다. CLI·서버가 같은 `load`/`loads`/`run`을 사용하는
단일 코어 공유 구조는 9.1절 의존성 다이어그램(D11)에 나타나 있다.
**Supplementation:** 없음.

## Q4: 대용량 이벤트 로그에서 리플레이 성능은 어떻게 확보하나?

**A:** 7.4절 — 스냅샷 시크 인덱싱. 로그를 K=2000 이벤트마다 스냅샷으로 인덱싱하고,
시크(seek)는 이분 탐색으로 스냅샷을 찾은 뒤 잔여 이벤트만 증분 재적용한다.
재생은 rAF 루프로 이벤트를 순차 적용하므로 로그 전체를 매번 다시 계산하지 않는다.
**Supplementation:** 없음 (D8 시퀀스 다이어그램과 함께 서술).

## Q5: 문서의 다이어그램·용어·수치가 실제 코드와 일치한다는 것을 어떻게 신뢰할 수 있나?

**A:** spec-driven 개발의 산출물이므로 3중 정합이 구조적으로 보장된다.
- 부록 A는 필드 표가 `sdv_sim/schema/arch.py`·`scenario.py`(Pydantic 모델)에 **1:1 대응**함을 명시한다 (A.0 정합).
- 부록 B는 본문이 인용하는 D-/F-/M-/T-번호를 spec(sdv-sim-v1/v2)의 절과 매핑한다 (B.3).
- 11장의 검증 수치는 실제 실행 결과(pytest 113건, mypy strict, spec-driven 검증 86/43 pass)를 근거로 한다.
**Supplementation:** 없음.

## Q6: 파일을 왜 브라우저가 직접 관리하나? 서버에 저장하는 편이 더 간단하지 않나?

**A:** 설계 중 방향 전환이 있었다. 최초 설계는 서버가 루트 폴더를 샌드박스로 관리하는 방식이었으나,
사용자 지시("서버에 저장한다는 개념은 부적절")로 **브라우저 로컬 파일 직접 관리**(FS Access API + 업로드/다운로드 폴백,
최근 파일은 IndexedDB)로 전환했다. 이에 따라 기존 `dashboard-run-path` ADR은 superseded 처리되고
F-11로 재설계되었으며, 서버는 파일 경로를 받지 않는 문자열 계약(2.4절 ④)을 유지한다.
**Supplementation:** 없음 (7.5절, 9.3절, 부록 B.2.1/F-11, 부록 C.3.2).

## Q7: 이 프로젝트를 직접 실행해보려면 어디서부터 시작해야 하나?

**A:** 실행 방법은 구조 설계서의 범위 밖이며 **README.md**에 정리되어 있다.
`uv sync --extra dev` 설치 → `uv run sdv-sim run samples/basic/...` (CLI) 또는
`uv run sdv-sim serve` (웹 대시보드: 편집 → 실행 → 리플레이 → 리포트, 스크린샷 포함).
**Supplementation:** 문서에는 5장(CLI 동작)과 8장(대시보드 흐름)의 계약 설명이 있고,
실행 절차는 README로 위임 — 별도 보강 없음 (README가 이미 안내).

## Q8: 앱 런타임의 스케줄링이 실제 차량 RTE(예: AUTOSAR)와 어떻게 대응하나?

**A:** 4.6절 — 비선점 주기 태스크 모델. 각 태스크는 `period_ms` 주기로 정수 ms tick에 실행되고,
`wcet_ms`를 초과하면 오버런으로 기록되며 다음 인스턴스는 스킵된다. 컴포넌트는 `Component`/`TaskContext`
API(`on_message`, `send`, `log`)로 작성되어 AUTOSAR SW-C의 메시지 기반 구조를 단순화한 형태로 대응한다.
구체적 근거는 D-19(컴포넌트 API)·D-20(스텁 동작) — 부록 B.1 참조.
**Supplementation:** 없음.

## Q9: 확장(v3 데스크톱, OTA, 다중 스위치)이 실제로 구조에 반영되어 있나?

**A:** 12장(향후 방향)은 각 후보가 어떤 기존 확장 지점(9.2절)에 연결되는지 표로 제시한다.
모든 후보는 코어 계약(`loads()`/`run()` + 이벤트 로그 형식)을 유지한 채 추가되도록 설계되어,
새 제공 형태·새 도메인·새 링크 동작이 각각 스키마 + 엔진 처리기 확장으로 흡수된다.
**Supplementation:** 없음 (방향성 언급만 허용 — overview Out of Scope 준수).
