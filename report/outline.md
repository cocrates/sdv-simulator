# Document Outline: SDV Simulator 구조 설계서 (v2)

> 문서 루트: `report/overview.md` 참조
> 날짜: 2026-08-13 (v2 — 사용자 피드백 반영)

## 본문과 부록의 역할 분담 (핵심 원칙)

- **본문**: "어떤 결정이 포함되었는지" — 최종 설계를 동작(flow)과 구조(모듈 의존성·확장성) 중심으로 설명. "왜 이렇게 결정했는가"의 근거 설명은 최소화 (부록 참조 표기).
  - ① 동작 측면: 시스템/모듈이 **어떤 플로우로 동작하는지**에 집중
  - ② 개발 측면: **모듈 간 의존성**과 **확장/변경 요구사항이 구조에 어떻게 반영**되었는지에 집중
- **부록**: 결정 근거와 참조 자료 (YAML 사양, Spec 요약, 개발 과정, ASR-ADR 검토 내역)

## 내러티브 아크 (Narrative Arc)

```
무엇을 만들었나(서론) → 전체 그림(시스템 개요) → 도메인 어휘(정의 형식 개요)
→ 동작의 심장부(코어 엔진) → 인터페이스(CLI → 대시보드 서버 → 프런트엔드)
→ 통합 흐름(데이터 흐름) → 개발 측면(모듈 의존성·확장성) → 운영(배포 → 품질)
→ 마무리(향후 → 결론) → 참조(부록 A~D)
```

## 목차 구조

### 1. 서론 (Introduction)
- **역할**: 문서의 목적·범위·구성 안내 + 과제 배경 제공.
- **내용**: 문서 목적/독자/범위(overview.md 요약), SDV 개념과 시뮬레이션 필요성, 버전 체계(v1/v2/v3)와 제공 형태, 본문/부록 역할 분담 안내.
- **분량**: 짧음 (약 1~2p)

### 2. 시스템 개요 (System Overview)
- **역할**: 전체 시스템의 한눈 구조. 이 문서의 "지도".
- **내용**: 시스템 목표·주요 기능, **전체 계층도(Mermaid D1)** — 코어/CLI/서버/프런트엔드/배포, 구성 요소와 기술 스택, 주요 설계 특성(결정성·단일 코어 공유·헤드리스/CI·브라우저 파일 경계)을 **최종 설계 사실**로 기술 (근거는 부록 C/D 참조 표기).
- **분량**: 중간 (약 2~3p)

### 3. 정의 형식 개요 (Definition Format Overview — 도메인 모델)
- **역할**: 시스템 입력 언어의 개념 지도. 이후 동작 설명의 어휘 기반.
- **내용**: 도메인 개념(노드/컴포넌트/태스크, 링크/프레임, 게이트웨이, 시나리오/메시지 주입/assertion)과 구조, **도메인 모델 다이어그램(Mermaid D2)**, Pydantic 스키마 검증이 하는 일(참조 무결성·유일성). **필드 단위 상세는 부록 A(YAML 사양) 참조**.
- **분량**: 중간 (약 2~3p)

### 4. 코어 시뮬레이션 엔진 (Core Simulation Engine) ★동작 중심 상세
- **역할**: 프로젝트의 심장부. "시뮬레이션이 어떻게 동작하는가"에 집중.
- **내용**:
  - 4.1 엔진 동작 모델: 이산 사건(DES) 진행, 정수 ms 시간, 결정적 이벤트 순서 `(t_ms, priority, decl, seq)` — 동작 규칙으로 서술
  - 4.2 런타임 구조: **클래스 다이어그램(Mermaid D3)** — `Simulator`/`LinkRuntime`/`TaskRuntime`/`NodeRuntime`/`ComponentRuntime`/`Attempt`
  - 4.3 실행 루프: **시퀀스 다이어그램(Mermaid D4)** — `run()` → tick별 이벤트 처리 → `link.drain()` 배치 해소 → 결과 정렬·리포트
  - 4.4 통신 동작: CAN(전송 시간 수식, ID 중재, 버스 큐잉) / Ethernet(스위치 FIFO, 테일 드롭, supersede) — **동작 흐름 다이어그램(Mermaid D5)**
  - 4.5 게이트웨이 라우팅 동작: 매칭 우선순위(frame > ID 범위), remap, 홉 제한 — **흐름 다이어그램(Mermaid D6)**
  - 4.6 앱 런타임 동작: 주기 태스크 스케줄링(비선점), 오버런·인스턴스 스킵, 컴포넌트 API(`Component`/`TaskContext`)와 스텁 동작
  - 4.7 검증·자동화 동작: assertion 평가 규칙(count ≥ n, at_ms), 이벤트 로그 7종, 리포트 생성
- **분량**: 김 (약 6~8p)

### 5. CLI (Command-Line Interface)
- **역할**: 코어를 감싸는 1차 제공 형태. 자동화/CI 인터페이스의 동작.
- **내용**: `run`/`serve` 명령과 옵션 동작, 실행 흐름(입력 → 로드 → 실행 → 로그/요약 → 종료 코드), 입출력 계약(로그 채널·`--log -`), 종료 코드 0/1/2/3의 의미, i18n 우선순위.
- **분량**: 짧음 (약 1~2p)

### 6. 대시보드 서버 (Dashboard Server)
- **역할**: v2의 백엔드. 브라우저 ↔ 코어를 잇는 API 계층의 동작.
- **내용**: 서버 구조(`create_app`, `Session`/`SessionStore`), **API 5종 동작 명세**(validate/run/load-log/events/report) — 각 엔드포인트가 무엇을 받고 돌려주는지, 오류 계약(F-8 envelope, 409 session_invalid), 세션 수명주기(교체·무효화), 로그 로드·리포트 파생 규칙(M-1: 파생 가능/불가 항목).
- **분량**: 중간 (약 3~4p)

### 7. 프런트엔드 (Frontend)
- **역할**: v2의 UI. 브라우저가 파일을 직접 관리하는 구조의 동작.
- **내용**:
  - 7.1 모듈 구조: 컴포넌트 맵과 역할
  - 7.2 상태 관리·라우팅 동작: `App.tsx` 소유 상태, `SessionMeta`, hash 라우팅
  - 7.3 구조 뷰 동작: SVG 렌더링, **결정적 레이아웃 알고리즘**(타입 밴드)이 그리는 방식
  - 7.4 리플레이 동작 ★: **시크 인덱싱 시퀀스(Mermaid D8)** — 스냅샷(K=2000)+잔여 재적용, 물리/펄스 모드, 오버레이 렌더링
  - 7.5 파일 접근 동작: FS Access API + 업로드/다운로드 폴백, IndexedDB 최근 파일
  - 7.6 편집·검증 피드백 동작: `useValidation`(500ms 디바운스, 서버 검증 권위)
  - 7.7 i18n 동작: 서버 주입 언어 → 브라우저 선택 → 로케일 폴백
- **분량**: 김 (약 5~7p)

### 8. 핵심 데이터 흐름 (Key Data Flows) ★통합 시퀀스
- **역할**: 앞선 섹션들을 하나로 묶는 통합 동작. "전체가 어떻게 움직이는가".
- **내용**: **run 경로 시퀀스(Mermaid D9)**(편집→검증→`POST /api/run`→세션 교체→이벤트/리포트 조회→리플레이), **load-log 경로 시퀀스(Mermaid D10)**, 재생·시크 흐름.
- **분량**: 중간 (약 2~3p)

### 9. 모듈 의존성과 확장·변경 반영 (Module Dependencies & Extensibility) ★개발 측면
- **역할**: "개발 측면" 초점 — 구조가 어떻게 모듈화되고, 확장/변경 요구를 어떻게 흡수하는가.
- **내용**:
  - 9.1 모듈 의존성: **의존성 다이어그램(Mermaid D11)** — `core`가 `cli`/`server`에 의존하지 않는 방향 규칙, schema↔core 관계, frontend→API 계약
  - 9.2 확장 지점: 커스텀 컴포넌트 등록(`components=`), 신규 링크 종류·라우트·assertion 추가, v2가 v1 코어를 **변경 없이** 재사용한 구조, v3 데스크톱 예정 경계
  - 9.3 변경 요구 반영 사례: F-11 방향 전환(`--root` 샌드박스 → 브라우저 파일 접근, `loads()` 문자열 API 추가 — 하위 호환 유지), `--host` 바인딩 정책 추가, 세션 무효화 이동(T-024) — 요구 변화가 구조에 어떤 영향 없이/적게 흡수되었는지
- **분량**: 중간 (약 3~4p)

### 10. 배포 (Deployment)
- **역할**: 실제 실행 환경. 구조의 완결성.
- **내용**: 패키징(hatchling, wheel에 정적 자산 강제 포함), serve 단일 프로세스·포트/바인딩 정책, systemd 서비스(`deploy/`).
- **분량**: 짧음 (약 1~2p)

### 11. 검증과 품질 (Verification & Quality)
- **역할**: 구조가 품질을 어떻게 보장하는지.
- **내용**: pytest(78건)·mypy strict, 프런트엔드 순수 로직 검증(`scripts/check-*.ts`), 샘플(`samples/`) 실행 검증.
- **분량**: 짧음 (약 1~2p)

### 12. 향후 방향 (Future Directions)
- **역할**: 현재 구조의 확장 지점 표시 (범위 외로 상세 없음).
- **내용**: v3 데스크톱, OTA, 다중 스위치 등 구조가 확장될 지점 (9.2와 연결).
- **분량**: 매우 짧음 (약 0.5~1p)

### 13. 결론 (Conclusion)
- **역할**: 문서 전체 요약 + 설계의 완성도 확인.
- **내용**: 핵심 구조 요약, overview.md 검증 기준 4가지 관점에서의 자체 점검(구조 파악 가능·핵심 설계 설명력·정합성·설계 근거).
- **분량**: 짧음 (약 1p)

## 의존성 그래프 (작성 순서)

```
1(서론) → 2(개요) → 3(정의 형식 개요) → 4(코어 엔진) → 5(CLI)
→ 6(서버) → 7(프런트엔드) → 8(데이터 흐름) → 9(모듈 의존성·확장성)
→ 10(배포) → 11(품질) → 12(향후) → 13(결론)
→ 부록 A(→3장 상세) → 부록 B(→4~8장 인용 번호 근거) → 부록 C(→2·9장 근거)
→ 부록 D(→3~10장 근거)
```

- 4장은 3장의 도메인 개념을 전제로 동작 서술
- 8장은 4·6·7장의 구성 요소를 조합 (통합 시퀀스)
- 9장은 앞선 모든 모듈 서술을 개발 관점에서 재구성 (마지막에 작성해 일관성 확보)
- 부록 A/B는 본문에서 참조되는 상세·근거 — 본문 작성 후 보강
